Reconciling drift across a 40-cluster GitOps fleet

Jul 18, 2026 · 11 min read · Bandung, Indonesia

The cluster didn't page us because it failed. It paged us because it succeeded, quietly, at a scale our alerting had never modeled.

Over eighteen months our platform team grew from four clusters to forty, spread across three cloud providers and one on-prem region. GitOps was supposed to make that growth uneventful. Mostly, it did. This is a record of the part that wasn't: a reconciliation loop that silently diverged for six weeks before anyone noticed.

The setup

Each cluster runs a reconciler polling a central manifest repository every ninety seconds. Under normal load this is unremarkable. At forty clusters, polling stopped being unremarkable.

What actually happened

A rate limit on the Git provider's API silently throttled exactly the clusters in our newest region. The reconciler treated a 429 as "no changes" rather than "unknown state," so it kept reporting healthy while quietly running six-week-old manifests.

reconciler.goGO
// BUG: 429 was treated as a no-op, not a retry-worthy failure
if resp.StatusCode == 429 {
    return nil // should have been: return ErrRateLimited
}

The fix was small. The instrumentation gap that let it run for six weeks was not.

Untested failure paths aren't absent. They're just unobserved.

What changed

We now treat "unknown" as a distinct reconciliation state from "healthy," and page on staleness rather than on error count alone. It's a small taxonomy change with an outsized effect on signal quality.
